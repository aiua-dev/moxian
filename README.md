# 墨线 moxian

面向中文长篇创作的连续性内核与 CLI。管伏笔、人物、时间线、设定与大纲，按章给 agent 递料。

A continuity kernel and CLI for long-form Chinese fiction. It tracks foreshadowing, character state, timeline, world rules and outlines, and hands an agent exactly the context it needs to draft the next chapter.

## 它防的是什么

长篇小说写到几十万字会开始崩，崩的地方永远是同一批：前面埋的伏笔忘了收、角色用了自己还不该知道的信息、时间线打结、世界规则自己打自己。这些不是文笔问题，是数据问题。正文是散文，散文里没法做校验。

墨线把这些数据从正文里拿出来，变成人能读、能查、能被程序校验的清单。它不替你写一个字，但会在你写坏之前拦住你。

## 四条设计原则

正文一个字符都不加标记。伏笔、认知、关系这些"按章发生的事"记在该章 frontmatter 里，复杂对象记在 `连续性/` 下的 YAML 里。frontmatter 本来就不是正文，任何 Markdown 工具都当元数据，所以复制正文去发布不可能带出标记。这不是靠纪律，是结构决定的。

目录与类型要少。一部作品一个根，根下三个目录，四类条目，五个编号前缀。对比同类的十八个目录、二十一种记录类型，这里刻意做减法。

没有审批链。写完就是写完，不存在"草稿 → 任务 → 候选 → 审批 → 验收 → 定稿"这种把写小说做成报批的流程。

校验分两级。结构上不成立的事（引用不存在的编号、时序倒置、两边对不上）在写入时就被拦住，磁盘上不留半成品；内容上可疑的事（悬空伏笔、角色提前知道真相、大纲偏离）只在跑校验时汇总，不打断写作。

## 安装

```bash
npm install -g moxian
```

需要 Node 20 以上。依赖只有 commander、yaml、zod。

## 快速开始

```bash
# 建一部作品。作品目录要与代码仓库分开，必须给一个空目录
moxian 初始化 ./雪夜断玉 --书名 "雪夜断玉" --作者 "YG"
cd 雪夜断玉

# 建章
moxian 章 新建 --卷 1 --标题 雪夜归人
moxian 章 新建 --卷 1 --标题 断玉现世

# 登记人物、设定、事件
moxian 人物 新建 --名 沈砚 --身份 "断玉阁少东家" --别名 沈三郎
moxian 人物 新建 --名 裴照 --身份 "靖安司提点"
moxian 设定 新建 --描述 "断玉能辨血脉" --类型 真相 --揭示 1-02
moxian 时间线 新建 --描述 "沈砚在雪夜拿到断玉"

# 埋一条伏笔，它会同时写进第 1-01 章
moxian 伏笔 新建 --描述 "断玉的来历" --埋 1-01 --预期回收 1-02

# 登记这一章发生的事。人物可以写名字，CLI 会解析成编号
moxian 章 登记 1-01 --事件 E-001 --认知 沈砚:S-001:已知
moxian 章 登记 1-02 --收 F-001 --关系 沈砚:裴照:敌对

# 拿写第三章所需的上下文，直接喂给 agent
moxian 打包 1-03

# 全量检查
moxian 校验
```

## 数据布局

```
雪夜断玉/
  作品.yaml              书名、作者、卷册结构
  正文/
    1-01-雪夜归人.md     frontmatter + 正文
    1-02-断玉现世.md
  大纲/
    总纲.md              自由文档，CLI 只读不解析
    1-第一卷 雪夜.md      卷大纲，带规划章列表
  连续性/
    伏笔.yaml
    人物.yaml
    时间线.yaml
    设定.yaml
```

章节文件的形状：

```markdown
---
章: 1-03
标题: 雪夜归人
叙事序: 12
摘要: 沈砚在雪夜拿到断玉
埋:
  - F-003
收:
  - F-001
事件:
  - E-007
认知:
  - 人物: P-001
    设定: S-002
    变为: 已知
关系:
  - 甲: P-001
    乙: P-002
    变为: 敌对
---

正文从这里开始，一个字都不加标记。
```

条目文件的形状：

```yaml
- 编号: F-001
  描述: 断玉的来历
  埋: 1-01
  预期回收: 1-02
  状态: 已收
  回收: 1-02
```

`叙事序` 是选填的。它只在闪回、插叙的时候才需要填，缺省就按写作序算。

## 编号

| 类别 | 形状 | 例 |
| --- | --- | --- |
| 章 | 卷-章 | `1-03` |
| 伏笔 | F-序号 | `F-001` |
| 人物 | P-序号 | `P-001` |
| 时间线 | E-序号 | `E-001` |
| 设定 | S-序号 | `S-001` |

编号由 CLI 分配，取现有最大序号加一，不复用空洞。章号是全书主键，人能读、能手搜、能背下来，没有 UUID。

## 命令

```
初始化 <目录> --书名 <书名> [--作者 <作者>]

章 新建 --标题 <标题> [--卷 1] [--章 1-03] [--摘要 <摘要>] [--正文文件 <路径>]
章 登记 <章号> [--埋 F-001,F-002] [--收 F-001] [--事件 E-001]
               [--认知 人物:设定:状态] [--关系 甲:乙:变化]
章 改 <章号> [--标题 <标题>] [--摘要 <摘要>] [--叙事序 <数字>]
章 显示 <章号>
章 列表 [--卷 1]

伏笔 新建 --描述 <描述> [--埋 <章号>] [--预期回收 <章号>] [--关联 F-001,P-001]
伏笔 收 <编号> --在 <章号>
伏笔 弃 <编号> [--原因 <原因>]
伏笔 改 <编号> [--描述 <描述>] [--预期回收 <章号>]
伏笔 列表 [--悬空]

人物 新建 --名 <名> [--别名 a,b] [--身份 <身份>] [--描述 <描述>]
人物 查 <人物> [--在 <章号>]
人物 列表

时间线 新建 --描述 <描述> [--时间 <说法>] [--前置 E-001]
时间线 列表
时间线 查 --章 <章号>

设定 新建 --描述 <描述> [--类型 规则|真相] [--生效 <章号>] [--揭示 <章号>]
设定 改 <编号> [--描述 <描述>] [--生效 <章号>] [--揭示 <章号>]
设定 列表 [--类型 真相]

卷 添加 --序号 <序号> --名 <名>
卷 列表

大纲 设置 --卷 <卷> [--名 <名>] [--规划 1-01,1-02] [--正文文件 <路径>]
大纲 查 [--卷 <卷>]
大纲 总纲

校验 [--只硬错|--只提醒]
打包 <章号> [--最近 3] [--输出 <路径>]
```

命令与选项一律中文。任何命令都能在作品目录或其子目录里跑。

## 校验规则

硬错，写入时拦住：

| 规则 | 含义 |
| --- | --- |
| E001 | 引用了不存在的编号 |
| E002 | 编号重复，或一个事件被两章声明 |
| E003 | 文件名与 frontmatter 里的章号不一致 |
| E004 | 同一章存在两个文件 |
| E005 | 时序倒置：回收早于埋设，或前置事件排在本事件之后 |
| E006 | 章节或大纲落在没登记的卷上 |
| E007 | 编号前缀与所在文件类型不符 |
| E008 | 状态与事实矛盾，例如标为已收却没有回收章 |
| E009 | 条目与章节两侧写的埋设章或回收章对不上 |

提醒，只在 `校验` 时汇总：

| 规则 | 含义 |
| --- | --- |
| W001 | 伏笔埋了 30 章还没收，也没规划回收章 |
| W002 | 过了预期回收章还没收 |
| W003 | 角色在真相对读者揭示之前就知道了 |
| W004 | 大纲规划了还没写的章 |
| W005 | 有正文但没有任何卷大纲规划它 |
| W006 | 两侧只写了一边 |

有硬错时 `校验` 退出码为 2。

## 给 agent 用

`打包 <章号>` 是这个工具给 agent 的主要接口。它输出一份 Markdown：作品与卷册信息、本卷大纲、本章已登记内容、截至上一章的角色认知与人物关系、未回收伏笔、生效设定、已发生事件、最近几章概要。不多不少，正好够写这一章。

配套的 `skills/moxian/SKILL.md` 是给 agent 读的操作说明，随包发布。

## 边界

CLI 只保证结构与可计算的时序。设定有没有被违反、人物口吻有没有漂移、这一章好不好看，这些语义判断不做，也做不到，那是 agent 读完递料内容后自己的判断。不假装能查语义。

## 开发

```bash
pnpm install
pnpm typecheck
pnpm test          # 先编译再跑 vitest
pnpm build
pnpm dev -- --help # 直接跑源码
```

测试分三层：编号与 frontmatter 的单元测试、校验引擎的规则测试、以及真正 spawn CLI 跑完整创作流程的端到端测试。
